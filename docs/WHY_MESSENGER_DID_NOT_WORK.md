# Messenger版がうまく動かなかった理由

調査日: 2026-09-24
対象: 現在の `main`（`e5a5ec3`）とリポジトリ内の実装・ドキュメント

## 結論

このリポジトリは、AIで返信文を作る部分よりも、その前後にあるMessengerへの接続と送信条件が目的に合っていません。現在の実装は「未承認のメッセージリクエストをブラウザーで見つけて分類し、必要なら返信案を作る」トリアージ用プロトタイプです。未承認リクエストに実際に返信する機能としては成立していません。

## 主な理由

1. **対象のメッセージに返信欄がない**
   `src/channels/messenger/watcher.ts` は「メッセージリクエスト」を走査します。未承認リクエストの画面には返信欄がなく、返信するにはリクエストの承認が必要です。このツールは承認操作を実装していません。返信欄がない場合は安全側に停止します。READMEも、リクエストについては検出・分類・返信案作成までのトリアージ専用と説明しています。

2. **実送信が初期設定で無効**
   `.env.example` は `DRY_RUN=true` で、さらに許可スレッドIDも空欄です。したがって初期設定ではMessengerへ送信しません。これを有効にしても、現在の監視対象である未承認リクエストに返信欄がない問題は解決しません。

3. **Facebook公式APIではなく、Web画面を操作している**
   PlaywrightでMessengerの画面を読み、`role`、`href`、`contenteditable` などのDOM属性を使って相手・未読状態・メッセージ欄を特定します。画面構造やラベルの変更、仮想スクロール、読込タイミングの変化で検出や送信が壊れる可能性があります。実送信ボタンのセレクターもREADMEとコードコメント上、実画面では未検証です。

4. **実画面での送信成功が確認されていない**
   READMEの実装ステータスは「Phase 5: 実装完了 / 実画面送信未検証」としています。テストはFake HTMLやモックDOMを通るシナリオを含みますが、本物のアカウントで受信から送信まで成功した証拠にはなりません。

5. **外部AIサービスの設定が別途必要**
   `.env.example` にはGemini APIキーが空欄です。既定ではJevは無効なのでGeminiが分類・返信文作成を担いますが、APIキーやブラウザーのログインセッションが適切に用意されなければ処理は進みません。現在の環境設定は確認していないため、これは設定時の条件であり、過去の失敗原因と断定はできません。

## 改善履歴から分かる不安定さ

現在の `main` に至る変更履歴では、実画面に合わせた修正が何度も必要になっています。たとえば、会話一覧の仮想化対応（PR #17）、未読行検出と一覧の読込待ち（PR #18）、ブラウザー評価コードの修正（PR #19）、Jev有効時のAPIキー不足を起動時に検出する修正（PR #20）が追加されています。これは、DOM連携や設定の組み合わせが動作上のボトルネックだったことを示します。

## 何ができて、何ができないか

| 現在の実装でできること | 現在の実装ではできない／確認できていないこと |
| --- | --- |
| Messengerのリクエスト画面をブラウザーで走査する | 未承認リクエストを自動承認して返信する |
| 受信文をAIで分類し、条件に応じた返信案を作る | 本物のMessenger画面で安定して送信できると保証する |
| 返信ガード、重複排除、送信上限、停止スイッチを適用する | 公式APIを使った安定した個人Messenger連携 |

## 今回の目的に照らした判断

このコードをそのまま社内チャットへ転用するより、AIによる「返信案生成」と人間による確認・送信を中心に据え、Mattermostの公式REST APIまたはプラグイン連携を使って作り直すのが適しています。送信まで自動化せず、最初は返信案を本人だけが見る下書き・通知として提示し、承認後に人間が投稿する設計にできます。

なお、この調査はソースコードとリポジトリ内ドキュメントのレビューです。実アカウントにログインした動作確認や過去の実行ログの調査は行っていないため、特定の過去エラーを断定するものではありません。
